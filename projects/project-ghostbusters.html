Project Ghostbusters

Which farmer are you gonna call?

Date Made
Summer 2024
Technologies
Python, Django, Vue.js

The problem

Grain trading involves a variety of factors, not least of which is distance. Freight costs can impact a farmer's decision to sell their grain to one buyer over another, which means that a buyer having the best bid for a particular transaction won't guarantee that they will get the transaction if they are too far away from the farmer. My task was to build a visualization for the tipping point for each farmer - the bid where, when factoring in freight costs and competitor bids, the farmer would find it more profitable to sell to a client than to a competitor. This visualization would take the form of a heatmap, allowing a user to take in the tipping points for many farmers at once, and thus allowing them to decide whose business they can gain most easily.

What I built

My solution was to add dedicated calculation logic to the backend to find out the best total profit for each farmer given that they would sell to a competitor and not to the user, as well as the freight cost for shipping to the elevator for which we wanted to run the calculation. By subtracting one from the other, we could find the bid that an elevator would have to make in order to sway a farmer to do business with them instead of a competitor. Running this optimization logic on each farmer produced a set of values that would then be sent to the frontend via a standard API endpoint and displayed in the form of a heatmap.

Challenges

The main issue facing this project was time. There were a high volume of farmers in the system, and the calculation for each individual farmer was fairly time-consuming. This meant running the full calculation every time the frontend sent a request would take a glacial amount of time. In response, I implemented two methods to speed up the user-experienced latency. First, I only ran the calculations on farmers nearby a user's elevators, using a convex hull with a buffered perimeter to determine candidate farmers. This meant that the only farmers on which the bid optimizer was run were those that were most likely to be affected by a change in bid. Second, I implemented a caching system to store the results of calculations for given parameters. At this point in the codebase's history, there was no existing caching system that I could fall back on; I had to build the first prototype myself. I used a hashmap to store results whenever a request with a set of parameters not matching anything in the cache was run, meaning duplicate requests would pull from the cache instead of performing the expensive optimization calculations. These design decisions helped to take a lot of strain off the backend and decreased the amount of time a user would be left waiting for calculations to finish.

What I learned

I completed Project Ghostbusters in under a week, and while my initial implementations weren't perfect, I was able to expand on my initial design and incorporate fixes for the slow initial behavior. I iterated on my first code, built a backend-heavy feature from scratch, and created a prototypical caching system that wasn't present in the codebase previously. Overall, my work on this project solidified my ability to build solid, functional features from scratch in the matter of a few days.
